# FULL DEVELOPMENT PROMPT — KPI Pivot Chart Creator

## 1. Project Overview

Build a complete, professional, high-performance desktop application named **KPI Pivot Chart Creator** using Python and PySide6.

The application imports CSV, TXT, XLSX, XLSM, and optionally XLSB files, allows users to select worksheets, configure date/time/grouping columns, select multiple KPI columns, configure filters and aggregation methods, generate interactive KPI dashboards, produce pivot-style summary tables, compare KPI values across days/months/years, and export results into multiple formats.

This application is primarily designed for telecom network performance analysis, RAN KPI monitoring, traffic analysis, availability monitoring, congestion analysis, and general time-series analytics.

### Core objectives

- Native desktop application.
- Windows-first deployment with a design that can also support macOS.
- Fully local file processing.
- No mandatory backend, cloud service, API, or external database server.
- Efficient processing of large datasets.
- Responsive UI during data processing.
- Multiple KPI and filter selection.
- Interactive dashboards and chart filtering.
- Automated daily, monthly, and yearly comparisons.
- Excel, CSV, Parquet, PNG, and PDF export.
- Clean, modular, maintainable architecture.
- Complete working source code and installation instructions.

Do not create a web application. This is a Python desktop application.

## 11. KPI Comparison Engine

Create a dedicated reusable comparison service.

Support three comparison periods:
- Daily.
- Monthly.
- Yearly.

The comparison engine must use the selected aggregation method and calculate each KPI independently.

Allow comparisons to be generated for the entire dataset or grouped by the selected Group column.

Apply the appropriate selected filters to both comparison periods.

### 11.1 Daily Comparisons

Provide these modes.

#### Mode A: Last Day vs Day-1

Compare the latest available reporting date against the immediately preceding calendar day.

Example:
- Latest Date: 18-Oct-2026.
- Previous Date: 17-Oct-2026.

Use the latest valid date available in the selected and filtered dataset.

#### Mode B: Last Day vs Day-7

Compare the latest available date against exactly seven calendar days earlier.

Example:
- Latest Date: 18-Oct-2026.
- Comparison Date: 11-Oct-2026.

Do not substitute the previous available record if the target date is missing.

If data is unavailable for the target date, mark the comparison as unavailable.

#### Mode C: Custom PRE Date vs POST Date

Provide two date pickers:
- PRE Date.
- POST Date.

Calculate each KPI for the two selected dates using the configured aggregation.

Validate that both dates are selected.

### 11.2 Monthly Comparisons

#### Mode A: Last Month vs Previous Month

Identify the latest available reporting month and compare it against the immediately preceding calendar month.

Example:
- Latest Month: September 2026.
- Previous Month: August 2026.

Do not use the last available record as a substitute for the previous month.

#### Mode B: Custom PRE Month vs POST Month

Provide month/year selectors for both periods.

Allow comparisons across different years.

Aggregate all qualifying records within each selected calendar month.

### 11.3 Yearly Comparisons

#### Mode A: Last Year vs Previous Year

Identify the latest available reporting year and compare it against the immediately preceding calendar year.

Example:
- Latest Year: 2026.
- Previous Year: 2025.

#### Mode B: Custom PRE Year vs POST Year

Allow the user to select both years independently.

Aggregate KPI values across each selected calendar year.

### 11.4 Comparison Results Table

For each selected KPI, generate these columns:

- KPI Name.
- Group, if selected.
- PRE Period.
- POST Period.
- PRE Value.
- POST Value.
- Absolute Change.
- Percentage Change.
- Comparison Status.

Calculation:

`Absolute Change = POST Value - PRE Value`

`Percentage Change = ((POST Value - PRE Value) / PRE Value) * 100`

If PRE Value equals zero, return `N/A` for percentage change.

If either value is missing, do not generate a misleading comparison.

### Comparison interpretation

Do not automatically treat positive changes as improvements.

For example:
- Increased traffic may be desirable.
- Increased CSSR may be desirable.
- Increased drop rate may be undesirable.
- Increased congestion may be undesirable.

Provide neutral change indicators by default. KPI-specific performance direction may be configurable later.

### Date logic

- Use actual date values internally.
- Respect calendar boundaries.
- Handle leap years.
- Handle missing days, months, and years.
- Never compare mismatched dates silently.
- Show the exact PRE and POST periods used.
- Apply consistent filters to both periods.
- Keep the comparison aggregation rules consistent.

## 12. Data Processing Architecture

Use a hybrid Polars + DuckDB architecture with a clearly defined execution strategy.

### Small and medium datasets

Use Polars for:
- Reading CSV.
- Selecting columns.
- Transformations.
- Filtering.
- Grouped aggregation.
- Date/time parsing.
- Daily, monthly, and yearly summaries.

### Large CSV and Parquet datasets

Use DuckDB SQL or Polars lazy/streaming execution based on the operation.

DuckDB can query CSV and Parquet directly without first loading every row into a Python list or a large pandas DataFrame.

Use temporary or persistent local DuckDB storage where appropriate.

### Excel input

Use the appropriate Excel reader to load only the requested worksheet and relevant columns when supported.

For large Excel worksheets, document unavoidable reader and memory limitations.

### Execution strategy

1. Inspect the source file.
2. Estimate data size and schema.
3. Select the appropriate reader.
4. Select the processing engine.
5. Load or scan required columns.
6. Normalize data types.
7. Apply worksheet and filter selections.
8. Calculate required aggregations.
9. Cache reusable intermediate results where appropriate.
10. Generate charts and comparison tables.
11. Export the requested results.
12. Release unused memory and temporary resources.

Do not process the same complete dataset through both Polars and DuckDB without a clear reason.

Avoid unnecessary DataFrame conversions and copies.

### Query safety

When generating DuckDB SQL:
- Properly quote identifiers.
- Use parameterized queries for values where supported.
- Never execute arbitrary SQL supplied by imported file contents.
- Validate all column mappings.
